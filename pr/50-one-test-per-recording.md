# test(goldens): one test per recording and per writer

Status: planned (2026-10-19, rehearsal feedback, Alex: "One test function that loops over everything? Then I get one
red test, not 37.") · Base: the goldens stack once merged (pr/07 adds the loop, pr/26 the writer loop) · Independent
code; touches only the two test files

## Why
The baseline ran as two `#[test]` functions. `every_set_matches_its_snapshots` looped over every recording with
`insta::glob!`, and `each_writer_on_the_same_generated_document` looped over the seven writers. A break showed as one
red test; the recording or writer was only in insta's summary, and the loop stopped at the first failing recording,
so whether the others were fine was unknown until that one was fixed.

## What changes
- `crates/toolpath-goldens/tests/goldens.rs`: one test per recording, generated by a `recording!` macro: `set_claude`,
  `set_codex`, `set_copilot`, `set_cursor`, `set_gemini`, `set_opencode`, `set_pi` (the
  `test-fixtures/<agent>/convo.*` sessions) and `set_claude_session`, `set_claude_compacted` (`goldens/<name>/input.*`).
  The temp `HOME` and every adapter store are set once, in a `OnceLock` every test enters before reading the
  environment (edition 2024's `set_var` is unsafe once threads run; tests now run in parallel). Each test sets
  insta's input file to its recording, so the failure summary names the file. New guard
  `every_recording_has_a_test`: a `convo.*` under `test-fixtures/` or an `input.*` under a non-agent `goldens/<name>/`
  without a test fails, naming the file (the glob picked new recordings up by itself; this keeps that).
- `crates/toolpath-goldens/tests/writers.rs`: one test per writer (`writer_claude` … `writer_cursor`) from a
  `writers!` macro over a shared, once-built document; the macro also emits an exhaustive `match` on `Agent`, so a new
  agent without a writer test does not compile.
- `crates/toolpath-goldens/tests/.qual`: resolves concern 2414bd5b (re-anchored from 53729a2d by pr/35; "sound only while this binary has one test"),
  reason fixed: the env writes now happen once, inside the `OnceLock`.
- Snapshot names, contents and headers unchanged (no `.snap` file in the diff). Running one recording:
  `cargo test -p toolpath-goldens --test goldens set_codex` (was `INSTA_GLOB_FILTER='codex/*'`).

Not changed: the stages inside a recording still stop at the first differing snapshot (insta's default); that one
failure names its snapshot (`ir@codex`) and line. `cargo insta test` still runs every stage.

## Verification
- `cargo test -p toolpath-goldens --test goldens --test writers`: 10 + 7 tests, all pass, no `.snap.new`.
- `INSTA_FORCE_UPDATE=1 INSTA_UPDATE=always` over both binaries: the snapshot bodies are byte-identical; the only
  rewrite is the `input_file:` header of 22 snapshots, which named the old `goldens/<agent>/input.jsonl` copy and now
  would name `test-fixtures/<agent>/convo.jsonl`. Reverted, not committed: metadata only (insta does not compare it),
  and several in-flight pieces touch these snapshots. Whoever next re-records them takes the corrected header.
- The break, on purpose and reverted (not committed): `"cwd"` in `test-fixtures/codex/convo.jsonl` set to
  `/broken-on-purpose`, then `cargo test -p toolpath-goldens --test goldens`:

  test set_gemini ... ok

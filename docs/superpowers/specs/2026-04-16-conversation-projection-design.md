# Conversation Projection Design

**Date:** 2026-04-16
**Branch:** akesling/incept
**Status:** Draft

## Goal

Enable projecting a toolpath document back into a functional agent conversation session. The primary use case is conversation portability between AI coding agents — a toolpath document derived from a Claude session can be projected into a format Codex or Gemini can resume from, and vice versa. The toolpath document is the interchange format.

Initial scope: **toolpath → Claude JSONL** projection only. The architecture supports future providers via the same trait.

## Design Principles

- The serde pattern: `ConversationProvider` (deserialize) already exists; add `ConversationProjector` (serialize). Both pass through `ConversationView` as the narrow waist.
- No new toolpath core types. Conversation data is modeled using existing Step/Path/ArtifactChange/StructuralChange types with a documented vocabulary (the conversation sub-protocol).
- Round-trip fidelity: `Claude JSONL → derive → Path → extract → ConversationView → project → Claude JSONL` should produce semantically equivalent output.

## Architecture

Three layers, clean separation:

```
toolpath          — the grammar (Step, Path, structural changes)
toolpath-convo    — the conversation sub-protocol (vocabulary + extraction + projection trait)
toolpath-claude   — Claude dialect (JSONL <-> sub-protocol)
```

### Data flow

```
Derive:   Claude JSONL → Conversation → ConversationView → toolpath Path
Project:  toolpath Path → ConversationView → Conversation → Claude JSONL
                          ↑ extraction        ↑ projection
                          (toolpath-convo)     (toolpath-claude)
```

Both directions pass through `ConversationView` as the narrow waist. M providers = M derive impls + M project impls, not M*N.

## Conversation Sub-Protocol (toolpath-convo)

A vocabulary built on toolpath's grammar for modeling conversations. Any provider that uses these structural change types and actor patterns gets extraction into `ConversationView` for free.

### Structural Change Types

#### `conversation.init`

Metadata about the session itself. One step at the start of a path.

Actor: `tool:<provider-name>` (e.g., `tool:claude-code` — the harness, not the model)
Artifact: `agent://<provider>/<session-id>` (virtual artifact)

Extra fields:
- `version` — agent/harness version string
- `working_dir` — absolute path to working directory
- `vcs_branch` — version control branch name
- `user_type` — user tier/type identifier
- Any additional provider-specific init data

#### `conversation.append`

A single conversational turn (user message or assistant response).

Actor: `human:<name>` for user turns, `agent:<model-or-agent-id>` for assistant turns
Artifact: `agent://<provider>/<session-id>` (virtual artifact)

Extra fields:
- `role` — `"user"` or `"assistant"`
- `text` — full message text (untruncated)
- `thinking` — internal reasoning / chain-of-thought (optional)
- `stop_reason` — why the turn ended (`"end_turn"`, `"tool_use"`, `"max_tokens"`)
- `model` — model identifier for this specific turn
- `input_tokens` — tokens sent to the model
- `output_tokens` — tokens generated by the model
- `cache_read_tokens` — tokens read from cache (optional)
- `cache_write_tokens` — tokens written to cache (optional)

#### `tool.invoke`

One or more tool invocations of the same tool type within a turn.

Actor: `agent:<agent-id>/tool:<ToolName>` (e.g., `agent:claude-code/tool:Read`)
Artifact key: file path for file tools, virtual artifact URN for others (e.g., `agent://claude/<session-id>/tool/shell/<tool-use-id>`)

Each artifact change has a structural change with:
- `type` — `"tool.invoke"`
- `tool_use_id` — provider-assigned invocation identifier
- `name` — tool name (e.g., `"Read"`, `"Bash"`, `"WebFetch"`)
- `input` — tool input parameters (JSON)
- `result` — tool output content (string, optional — absent if no result yet)
- `is_error` — whether the tool reported an error (boolean, default false)
- `category` — toolpath category (`"file_read"`, `"file_write"`, `"file_search"`, `"shell"`, `"network"`, `"delegation"`)

### Actor Patterns

- `human:<name>` — a human user
- `agent:<id>` — an AI model or agent (the model producing text/decisions)
- `agent:<id>/tool:<ToolName>` — the tool subsystem of an agent
- `tool:<name>` — a standalone tool or harness (not a model)

### Artifact URN Scheme

Non-file tool invocations and conversation sessions are **virtual artifacts** — they don't correspond to files on disk but are tracked as artifacts in the toolpath document for provenance. All virtual artifacts use the `agent://` scheme with provider as a path segment:

```
agent://<provider>/<session-id>                          — the conversation itself
agent://<provider>/<session-id>/tool/shell/<tool-use-id> — a shell invocation
agent://<provider>/<session-id>/tool/web/<tool-use-id>   — a web fetch
agent://<provider>/<session-id>/tool/task/<tool-use-id>  — a delegation
```

Examples:
```
agent://claude/abc-123-def                          — a Claude conversation
agent://claude/abc-123-def/tool/shell/tu_98765      — a Bash invocation in that session
agent://codex/session-456                           — a Codex conversation
agent://gemini/session-789/tool/web/tu_11111        — a web fetch in a Gemini session
```

File tools (Read, Write, Edit, Glob, Grep) use the actual file path as the artifact key — they change real file artifacts, not conversation-scoped resources.

### Step Structure

A typical assistant turn with tool use produces multiple steps:

1. **Conversation step** — actor `agent:claude-code`, structural change `conversation.append` on the conversation artifact. Contains text, thinking, token usage, stop reason.
   - Step ID: the turn's unique identifier (e.g., the original UUID)
   - Parents: the previous conversation step

2. **Tool step(s)** — one per distinct tool type used in the turn. Actor `agent:claude-code/tool:Read`. Multiple invocations of the same tool collapse into one step with multiple artifact changes. If the same tool targets the same artifact twice (e.g., two Bash commands), each invocation is a separate artifact change keyed by `tool_use_id` rather than target path.
   - Step ID: derived from the turn ID + tool name
   - Parents: the conversation step from (1)

User turns are a single conversation step with no tool steps.

### Parent Chain

Steps form a linear chain for the conversation backbone:

```
init → user-1 → assistant-1 → user-2 → assistant-2 → ...
                    |
                    ├── tool:Read (2 files)
                    └── tool:Edit (1 file)
```

Tool steps are children of their assistant turn. Sidechain/branching conversations use the standard toolpath parent mechanism.

## toolpath-convo Changes

### New dependency

`toolpath-convo` gains a dependency on `toolpath` (core types). This enables the extraction function to operate on `toolpath::v1::Path` directly.

### `ConversationProjector` trait

```rust
pub trait ConversationProjector {
    type Output;
    fn project(&self, view: &ConversationView) -> Result<Self::Output>;
}
```

Concrete callers use the trait directly with full type safety.

### `AnyProjector` type-erasing wrapper

```rust
pub struct AnyProjector(Box<dyn ErasedProjector>);

// Internal trait for type erasure
trait ErasedProjector {
    fn project_erased(&self, view: &ConversationView) -> Result<Box<dyn Any>>;
}

impl<T: ConversationProjector + 'static> ErasedProjector for T
where
    T::Output: 'static,
{
    fn project_erased(&self, view: &ConversationView) -> Result<Box<dyn Any>> {
        self.project(view).map(|o| Box::new(o) as Box<dyn Any>)
    }
}

impl AnyProjector {
    pub fn new<P: ConversationProjector + 'static>(p: P) -> Self
    where
        P::Output: 'static;

    pub fn project(&self, view: &ConversationView) -> Result<Box<dyn Any>>;

    /// Project and downcast to the expected type. Returns Err if the
    /// downcast fails or the projection fails.
    pub fn project_as<T: 'static>(&self, view: &ConversationView) -> Result<T>;
}
```

### Extraction function

```rust
/// Extract a ConversationView from a toolpath Path that follows the
/// conversation sub-protocol.
///
/// Walks the step DAG in topological order, recognizes conversation.init,
/// conversation.append, and tool.invoke structural changes, and assembles
/// them into a ConversationView.
pub fn extract_conversation(path: &toolpath::v1::Path) -> ConversationView;
```

Logic:
1. Walk steps in topological order (respecting parent links)
2. For each step, examine structural changes:
   - `conversation.init` → populate ConversationView metadata (provider_id, session info)
   - `conversation.append` → create a Turn with text, thinking, role, usage, etc.
   - `tool.invoke` → create ToolInvocation entries, attach to the parent turn
3. Actor pattern matching determines role:
   - `human:*` → Role::User
   - `agent:*` (no `/tool:`) → Role::Assistant
   - `*/tool:*` → tool invocation, not a turn
4. Assemble parent-child relationships for tool steps → Turn.tool_uses

## toolpath-claude Changes

### Enriched derive (`derive.rs`)

Current `derive_path()` is upgraded to produce sub-protocol-compliant output:

**Conversation turns:**
- Full untruncated text (remove 2000-char truncation)
- Thinking blocks included by default (flip `include_thinking` default)
- Full UUIDs as step IDs (remove 8-char prefix truncation)
- Token usage fields in `conversation.append` extra
- `stop_reason` and `model` in `conversation.append` extra
- `requestId` and `messageId` as `StepMeta.refs` entries

**Tool invocations:**
- Separate steps per tool type per turn
- Actor: `agent:claude-code/tool:<Name>`
- Full tool input JSON and result content as structural change fields
- Proper artifact keys (file paths for file tools, URNs for others)
- Tool category classification

**Init entries:**
- `conversation.init` step with version, cwd, gitBranch
- Actor: `tool:claude-code`

**Environment snapshots:**
- `cwd` and `gitBranch` captured in `conversation.init` and optionally per-turn

### `ConversationProjector` implementation

`ClaudeConvo` (or a new `ClaudeProjector` type) implements `ConversationProjector`:

```rust
impl ConversationProjector for ClaudeProjector {
    type Output = Conversation;

    fn project(&self, view: &ConversationView) -> Result<Conversation>;
}
```

The projection maps ConversationView back to Claude's native types:

- **Init turn** → `ConversationEntry` with type `"init"`, version/cwd/gitBranch fields
- **User turns** → `ConversationEntry` with `MessageRole::User`, text content
- **Assistant turns** → `ConversationEntry` with `MessageRole::Assistant`, content parts:
  - Text → `ContentPart::Text`
  - Thinking → `ContentPart::Thinking`
  - Tool uses → `ContentPart::ToolUse` (from Turn.tool_uses)
- **Tool results** → separate `ConversationEntry` with `MessageRole::User`, content parts of type `ContentPart::ToolResult` (Claude's tool-result-only user entry pattern)
- **Token usage** → `Message.usage` fields
- **UUIDs** → step IDs become entry UUIDs
- **Session ID** → extracted from conversation artifact URN (`agent://claude/<session-id>`)
- **Parent chain** → `parentUuid` from step parents

### Best-effort mapping for non-Claude sources

When the ConversationView came from a non-Claude provider:
- Generate UUIDs for entries (deterministic from turn IDs if possible)
- Generate a session ID from the ConversationView.id
- Map tool invocations to Claude tool names by category (e.g., `ToolCategory::FileRead` → `"Read"`, `ToolCategory::Shell` → `"Bash"`)
- Use sensible defaults for missing fields (version, userType, etc.)

## Testing Strategy

### Unit tests (per crate)

**toolpath-convo:**
- `extract_conversation` correctly identifies conversation.init, conversation.append, tool.invoke steps
- Actor pattern matching for role assignment
- Tool steps attached to correct parent turns
- Handles paths with no conversation sub-protocol steps gracefully

**toolpath-claude:**
- Enriched derive produces sub-protocol-compliant output
- Full text preservation (no truncation)
- Tool invocations as separate steps with correct actors
- Projector maps ConversationView → Conversation correctly
- Tool result entries generated for tool uses with results
- Best-effort mapping for non-Claude ConversationViews

### Round-trip test (integration, toolpath-cli)

```
Claude JSONL → derive → Path JSON → extract → ConversationView → project → Claude JSONL
```

Assert semantic equivalence:
- Same number of user/assistant turns
- Same message text content
- Same tool invocations (names, inputs, results)
- Same token usage values
- Same parent chain structure
- Same session metadata (where recoverable)

Not asserted (acceptable losses):
- Byte-identical JSON (field ordering, whitespace)
- Fields that are genuinely unrecoverable from the toolpath document (e.g., internal API fields that were never captured)

## Migration / Compatibility

The enriched derive produces a different (richer) toolpath output than the current derive. This is a **minor version bump** for `toolpath-claude` (pre-1.0, so minor = potentially breaking):

- **Breaking:** Conversation artifact key changes from `claude://<session-id>` to `agent://claude/<session-id>`. Consumers that pattern-match on `claude://` artifact keys must update.
- **Breaking:** Tool invocations are now separate steps (previously inlined as name lists in `conversation.append`). Consumers counting steps or iterating them will see more steps.
- **Breaking:** Step IDs use full UUIDs instead of 8-char prefixes. Any consumer storing or referencing step IDs will see different values.
- **Additive:** Richer `conversation.append` extra fields (full text, thinking, usage, stop_reason, model).
- **Additive:** `conversation.init` steps (previously skipped).

`toolpath-convo` gets a minor version bump for the new trait, extraction function, and `toolpath` dependency.

## Open Questions

1. **Thinking signatures** — Claude's thinking blocks carry cryptographic signatures. These could map to `StepMeta.signatures` but the semantics differ (signing a content block vs. the whole step). Defer to a follow-up.
2. **Session chains** — Claude Code rotates JSONL files on context overflow. The enriched derive should produce multiple paths (one per segment) or a single merged path. Current behavior merges; projection needs to handle both.
3. **Delegation / sub-agents** — Tool invocations of type `Task` (delegation) spawn sub-agent sessions. These are currently modeled as `DelegatedWork` in ConversationView. The sub-protocol should define how delegations appear in the step DAG. Defer to a follow-up.
